A structural standard model for Web5 — style-free and framework-agnostic, designed to be read and regenerated by humans and machines.

ConstructOS — Structural Standard Model (Web5)

ConstructOS is a structure-first, style-free standard model for building websites, applications, simulators, and games. It defines a deterministic grammar: a small set of nodes and regions that describe where things may exist and how they relate — independent of CSS systems, frameworks, or runtime behavior.

This document is a foundational reference, not a framework manual or component catalog. It explains what the structural grammar is, what is guaranteed to stay stable, and which parts (themes, schemes, runtimes) are intentionally left open for interpretation.

The same grammar applies to three high-level contexts: system, application, and website. This document uses the website context in its examples, but the underlying rules are shared.

If you are new to ConstructOS, you can read this in order:

  • Sections 1–2 — why ConstructOS exists and the Web1→Web5 framing.
  • Sections 3–5 — core structures, layout structures, and sub-structures (the main grammar).
  • Sections 6–7 — scope axes and utilities (how interpretation is targeted).
  • Sections 8–9 — CSS and JavaScript layers (how interpretation is applied).
  • Section 10 — a minimal, copy-pasteable ConstructOS website.
  • Section 11 — a short glossary of key terms.
  • Sections 12–13 — who this is for, non-goals, and how the grammar evolves.

1. Why ConstructOS exists

Modern front-end systems drift over time. Markup reflects a framework’s opinions, CSS mixes layout and semantics, and JavaScript quietly becomes the true source of structure. After a few years it is difficult to answer a simple question:

“What is this system, structurally?”

ConstructOS addresses this by defining a small, explicit grammar that belongs to the document itself. Frameworks, design systems, and runtimes sit on top as interpreters of that grammar — not as owners of it.

  • Structure is explicit and fixed. Node names and regions are small in number and strictly defined.
  • Interpretation is layered. Layout, appearance, tone, and behavior are independent layers.
  • Regeneration is expected. Given the same structure, data, and scope, you should get equivalent outputs.

The goal is not to replace existing tools. The goal is to give every tool the same structural contract, so systems can evolve without losing their identity or requiring repeated structural rewrites.

2. Web1 → Web5 in one view

ConstructOS uses “Web5” as shorthand for deterministic, regenerable web experiences. One way to frame the journey:

  • Web1 — Documents
    Static pages. Content and presentation are tightly coupled; reuse is limited.
  • Web2 — Applications
    Rich interactivity and component frameworks. Structure is often implicit in templates and JavaScript.
  • Web3 — Ownership
    Identity and verification layers added to existing applications. The underlying structural patterns stay mostly the same.
  • Web4 — Automation
    Generators, design systems, and low-code tools. Structure is inferred from tools and assets instead of being defined as a stable contract.
  • Web5 — Deterministic systems
    Explicit structure, data-driven variation, and regenerable outputs. The same structural document can be reinterpreted across time, tools, and platforms without losing meaning.

ConstructOS lives in this Web5 space. It does not replace technologies; it provides a neutral, strict core that they can all operate on.

3. Core structures (site → page → regions)

ConstructOS defines a small set of core nodes that every web-facing experience should recognize:

  • site — the root container for a website.
  • page — a single navigable surface.
  • global-header — optional, cross-site identity and navigation.
  • page-header — page-level heading, intro, and meta.
  • page-body — primary content surface (sections and cells live here).
  • page-footer — page-scoped closing region.
  • global-footer — shared site-level footer.

Multi-page experiences are composed of multiple documents. Each document implements this same site → page → region grammar with a single site and single page, and shares a common data-ct-type, data-ct-source, data-ct-theme, data-ct-scheme, data-ct-tone, and data-ct-mode contract across pages.

These nodes are always expressed using the same pattern: 


<div class="ct-node-wrapper" data-ct-node="site">
    <div class="ct-site">
        <div class="ct-node-wrapper" data-ct-node="page">
            <div class="ct-page">

                <div class="ct-node-wrapper" data-ct-node="global-header">
                    <header class="ct-global-header">...</header>
                </div>

                <div class="ct-node-wrapper" data-ct-node="page-header">
                    <header class="ct-page-header">...</header>
                </div>

                <div class="ct-node-wrapper" data-ct-node="page-body">
                    <main class="ct-page-body">...</main>
                </div>

                <div class="ct-node-wrapper" data-ct-node="page-footer">
                    <footer class="ct-page-footer">...</footer>
                </div>

                <div class="ct-node-wrapper" data-ct-node="global-footer">
                    <footer class="ct-global-footer">...</footer>
                </div>
            </div>
        </div>
    </div>
</div>

Global invariants:

  • Exactly one site per document.
  • Exactly one page per document.
  • At most one of each core region per page: global-header, page-header, page-body, page-footer, global-footer.
  • Every ct-node-wrapper has exactly one direct core child (for example .ct-site, .ct-page, .ct-page-body).
  • data-ct-node defines semantics; class="ct-…" mirrors the node name but carries no additional meaning.

These invariants are deliberately strict. A strict structural core enables flexible theming, runtime behavior, and tooling on top.

4. Layout structures (sections and cells)

Layout inside page-body is defined with two nodes: section and cell.

  • section
    A layout block inside a region. Each section groups one to three cells.
  • cell
    A layout slot inside a section. Cells host sub-structures (collections, feeds, components, elements).

Sections do not nest inside other sections, and cells do not contain sections. This keeps the layout graph shallow and predictable.

Values for data-ct-cell (for example primary, secondary, tertiary) are layout hints interpreted by themes and schemes. They do not introduce new structural types and should come from a small, predictable vocabulary.

Layout invariants:

  • Each section contains between one and three cells.
  • Cells may repeat, but they do not nest other cells or sections.
  • Grids and flex layouts are interpretations inside cells, not new structural nodes.

<div class="ct-node-wrapper" data-ct-node="page-body">
    <main class="ct-page-body">

        <!-- main hero section -->
        <div class="ct-node-wrapper" data-ct-node="section">
            <section class="ct-section">

                <!-- primary cell -->
                <div class="ct-node-wrapper" data-ct-node="cell" data-ct-cell="primary">
                    <div class="ct-cell">
                        <!-- sub-structures live here -->
                    </div>
                </div>

                <!-- secondary cell -->
                <div class="ct-node-wrapper" data-ct-node="cell" data-ct-cell="secondary">
                    <div class="ct-cell">
                        <!-- sub-structures live here -->
                    </div>
                </div>
            </section>
        </div>
    </main>
</div>

Cells are layout slots only. Grid, flex, spacing, and breakpoints are decided by theme and scheme layers — not by adding more structural nodes.

5. Sub-structures (collections, feeds, components, elements, tags)

Inside a cell, ConstructOS uses sub-structures to describe what is being rendered:

  • collection — owns a set of related items (data set).
  • feed — iterates and displays items from a data source.
  • component — reusable UI unit (card, nav, badge, widget).
  • element — atomic content or control.
  • tag — semantic HTML output at the leaves.

Collections and feeds are about grouping and iteration. Components and elements are about presentation and interaction. Tags are the final semantic HTML emitted at the edges of the tree. 


<!-- a primary cell hosting a collection of articles -->
<div class="ct-node-wrapper" data-ct-node="cell" data-ct-cell="primary">
    <div class="ct-cell">

        <!-- collection: articles -->
        <div class="ct-node-wrapper" data-ct-node="collection" data-ct-collection="articles">
            <div class="ct-collection">

                <!-- feed: grid view over article data -->
                <div class="ct-node-wrapper" data-ct-node="feed" data-ct-display="grid">
                    <div class="ct-feed">

                        <!-- component: article-card (single item) -->
                        <div class="ct-node-wrapper" data-ct-node="component" data-ct-component="article-card">
                            <div class="ct-component">

                                <!-- element: title -->
                                <div class="ct-node-wrapper" data-ct-node="element" data-ct-element="title">
                                    <div class="ct-element">
                                        <h2>Article title</h2>
                                    </div>
                                </div>

                                <!-- element: summary -->
                                <div class="ct-node-wrapper" data-ct-node="element" data-ct-element="summary">
                                    <div class="ct-element">
                                        <p>Short summary of the article...</p>
                                    </div>
                                </div>
                            </div>
                        </div>
                    </div>
                </div>
            </div>
        </div>
    </div>
</div>

Constraints:

  • Collections define sets of items; they do not own layout.
  • Feeds render items; they do not contain other feeds or collections.
  • Components are atomic; components do not contain other components.
  • Elements are leaves; they do not contain components, feeds, or collections.
  • Tags are plain HTML; they never carry data-ct-* attributes and are class-free by default.
  • Raw content (if present) is opaque to ConstructOS and not structurally parsed. Any HTML outside ct-node-wrapper structures is considered raw.

The following patterns are explicitly invalid and SHOULD be treated as errors by tools and runtimes:

  • section must not contain another section or a nested cell tree.
  • cell must not contain section or other cell nodes.
  • collection must not contain collection or feed nodes.
  • feed must not contain collection or feed nodes.
  • component must not contain other component nodes.
  • element must not contain collection, feed, component, or element nodes.
  • tag must never carry any data-ct-* attributes.

These constraints keep the subtree under each cell shallow, predictable, and safe to traverse and regenerate.

6. Scope axes (type, source, theme, scheme, tone, mode)

At the document root, ConstructOS uses a fixed attribute order to define interpretation scope: 


<html
    lang="en"
    data-ct-type="website"
    data-ct-source="example-site"
    data-ct-theme="layout-core"
    data-ct-scheme="neutral"
    data-ct-tone="technical"
    data-ct-mode="wireframe"
    ...
></html>

These attributes define independent axes:

  • data-ct-type — context type (for example website, application, system, game).
  • data-ct-source — asset and data namespace (brand, product, environment).
  • data-ct-theme — layout model and structural rules.
  • data-ct-scheme — appearance model (color, typography, surfaces).
  • data-ct-tone — language and voice model (UX copy, messaging).
  • data-ct-mode — visualization mode (wireframe, light, dark, debug…).
  • extras — additional attributes (for example data-ct-app-src or data-ct-web-src for linked contexts).

The same grammar applies regardless of context type; only the data and interpretation layers change.

Region targeting and local overrides:

  • Scope attributes (source, theme, scheme, tone, locale) may be applied to the html element or to wrapper nodes for site, page, and core regions (global-header, page-header, page-body, page-footer, global-footer).
  • Local overrides use explicit data-ct-local-* attributes on the relevant wrapper node (for example data-ct-local-source, data-ct-local-theme, data-ct-local-scheme, data-ct-local-tone, data-ct-local-mode, data-ct-local-locale). These attributes terminate inheritance for that axis beneath that node.
  • Scope attributes must not be applied to arbitrary inner nodes or tags; this keeps targeting predictable and easy to reason about.

7. Utilities (page and global)

Utilities are intentional constructs that live alongside the main layout, not inside it. They are used for overlays, dialogs, drawers, notifications, and other stateful UI that should not distort the core site → page → region structure.

  • Page utilities — scoped to a specific page.
  • Global utilities — shared across the whole experience.

Utilities are hidden by default and are usually inserted near the end of the document body so they load before scripts bind behavior. 


<!-- page utilities (inside the same document, outside normal flow) -->
<div class="ct-page-utilities" hidden>

    <div class="ct-node-wrapper" data-ct-node="utility" data-ct-utility="modal-dialog">
        <div class="ct-utility">
            <!-- modal content here -->
        </div>
    </div>
</div>

<!-- global utilities (shared across pages) -->
<div class="ct-global-utilities" hidden>

    <div class="ct-node-wrapper" data-ct-node="utility" data-ct-utility="notification-center">
        <div class="ct-utility">
            <!-- notification stack here -->
        </div>
    </div>
</div>

JavaScript runtimes typically activate utilities by changing state (attributes, classes, or dataset flags); utilities themselves do not own business logic. They are structural placeholders for higher-level behavior.

8. CSS interpretation layers (theme, scheme, mode)

ConstructOS separates layout and appearance into dedicated CSS layers. The HTML does not encode design decisions; it exposes stable targets for CSS to interpret.

  • Theme — layout: grid/flex behavior, spacing, geometry, breakpoints.
  • Scheme — appearance: color, typography, surfaces, depth, motion.
  • Mode — visualization overlays: wireframe, light, dark, debug, high-contrast.

<!-- layout theme (structure-oriented CSS) -->
<link rel="stylesheet" href="css/core.css">
<link rel="stylesheet" href="css/theme.css">

<!-- appearance scheme (visual CSS) -->
<link rel="stylesheet" href="css/scheme.css">



/* example: theme layout variables (structure) */
:root {
    --custom-theme-site-max-width: 1120px;
    --custom-theme-page-padding-inline: 24px;
}

/* example: scheme appearance variables (style) */
:root {
    --custom-scheme-site-background: #ffffff;
    --custom-scheme-text-color: #111111;
}

A recommended ordering for CSS is:

  • 1. Structural layout (theme).
  • 2. Appearance (scheme).
  • 3. FX and motion layers.
  • 4. Mode-specific overlays (wireframe, debug, etc.).

CSS selectors should generally resolve scope-first (from the nearest data-ct-* attributes), then structural roles ([data-ct-node="section"], [data-ct-node="cell"], etc.), and finally any custom-* tokens for design-system specifics. This keeps structural semantics separate from styling concerns.

9. JavaScript interpretation layers (data, variables, config, functions, boot)

JavaScript treats the ConstructOS document as input: a tree of nodes, attributes, and tokens. It does not own structure; it interprets and augments it.

  • Data (source) — derived from data-ct-source and other attributes.
  • Variables — runtime values (viewport, user state, active mode).
  • Config — declarative mappings between structure, data, and behavior.
  • Functions — operations that respond to the structural model.
  • Boot — startup routines that wire everything together.

<script>
(function () {

    // 1. Read scope from the document root
    var root = document.documentElement;

    var context = {
        type:   root.getAttribute('data-ct-type'),
        source: root.getAttribute('data-ct-source'),
        theme:  root.getAttribute('data-ct-theme'),
        scheme: root.getAttribute('data-ct-scheme'),
        tone:   root.getAttribute('data-ct-tone'),
        mode:   root.getAttribute('data-ct-mode')
    };

    // 2. Query structural nodes
    var site = document.querySelector('[data-ct-node="site"]');
    var pages = site
        ? site.querySelectorAll('[data-ct-node="page"]')
        : [];

    // 3. Example: attach behavior without changing structure
    pages.forEach(function (page) {
        var feeds = page.querySelectorAll('[data-ct-node="feed"]');
        feeds.forEach(function (feed) {
            // interpret data-ct-display (grid, list, carousel, ...)
            var displayMode = feed.getAttribute('data-ct-display') || 'grid';
            feed.dataset.ctDisplayResolved = displayMode;
        });
    });

    // 4. Boot complete
    root.setAttribute('data-ct-boot', 'complete');

}());
</script>

JavaScript SHOULD mutate state, not core structure. It should not add, remove, or reorder core regions, sections, or cells at runtime. Instead it:

  • reads structural intent from data-ct-*,
  • manages utilities and stateful overlays,
  • binds data sources and transforms,
  • updates attributes and classes that express state.

A useful mental model is: State → Scope → Behavior. Structure stays stable underneath.

10. Minimal ConstructOS website


<!doctype html>
<html lang="en" data-ct-type="website" data-ct-source="example" data-ct-theme="layout-core" data-ct-scheme="neutral" data-ct-tone="technical" data-ct-mode="wireframe">

    <head>
        <meta charset="utf-8">
        <meta name="viewport" content="width=device-width,initial-scale=1">
        <title>Example ConstructOS Site</title>
    </head>

    <body>
        <div class="ct-node-wrapper" data-ct-node="site">
            <div class="ct-site">

                <div class="ct-node-wrapper" data-ct-node="page">
                    <div class="ct-page">

                        <div class="ct-node-wrapper" data-ct-node="page-body">
                            <main class="ct-page-body">

                                <div class="ct-node-wrapper" data-ct-node="section">
                                    <section class="ct-section">

                                        <div class="ct-node-wrapper"
                                             data-ct-node="cell"
                                             data-ct-cell="primary">
                                            <div class="ct-cell">

                                                <div class="ct-node-wrapper"
                                                     data-ct-node="element"
                                                     data-ct-element="title">
                                                    <div class="ct-element">
                                                        <h1>ConstructOS — structure only</h1>
                                                    </div>
                                                </div>
                                            </div>
                                        </div>
                                    </section>
                                </div>
                            </main>
                        </div>
                    </div>
                </div>
            </div>
        </div>
    </body>
</html>

This example shows the smallest practical ConstructOS website: one site, one page, one region, one section, one cell, one element. It is verbose by design so that both humans and machines can read intent directly from the structure.

To evolve this into a real project:

  • Keep the wrapper pattern (ct-node-wrapper → single core child) unchanged.
  • Add sections and cells for layout, but never nest sections or cells inside each other.
  • Introduce collections, feeds, components, and elements inside cells as needed.
  • Attach your own layout and appearance via themes, schemes, and modes instead of changing the grammar.

11. Glossary (core terms)

Context
High-level type of construct: system, application, website, or game. Declared with data-ct-type. The grammar is shared across contexts.

Site
Root container for a website experience. Exactly one per document.

Page
Single navigable surface inside a site. Exactly one per document.

Region
Named page area: global-header, page-header, page-body, page-footer, global-footer. Each region appears at most once per page.

Section
Layout block inside a region. Groups one to three cells.

Cell
Layout slot inside a section (for example primary, secondary, tertiary). Hosts sub-structures; does not contain other cells or sections.

Collection
Structural owner of a set of related items (a data set). Does not own layout.

Feed
Renderer that iterates over a collection or data source. Does not contain other feeds or collections.

Component
Reusable UI unit (card, nav, badge, widget). Atomic; does not contain other components.

Element
Atomic presentational unit (text, control, icon). Does not own structural children such as components, feeds, or collections.

Tag
Native HTML output at the leaves. Class-free by default and never carries data-ct-* attributes.

Utility
Structural placeholder for overlays, dialogs, drawers, and other out-of-flow UI. Hidden by default and activated via state.

Theme
CSS layer that defines layout behavior: spacing, grids, responsive rules. Selected via data-ct-theme.

Scheme
CSS layer that defines appearance: color, typography, surfaces, motion. Selected via data-ct-scheme.

Mode
Visualization layer (wireframe, light, dark, debug, high-contrast). Selected via data-ct-mode.

12. Who this is for

ConstructOS is intended for developers, system designers, and tool builders who care about:

  • long-lived, multi-brand experiences that must survive framework changes,
  • clear separation between structure, layout, appearance, and behavior,
  • automation and regeneration of documents from intent and data,
  • structural contracts that engines and other systems can rely on without guesswork.

ConstructOS is not:

  • a visual design system,
  • a component library,
  • a CSS framework,
  • a JavaScript framework.

It is a structural standard model that other systems can build on. Those systems are free to evolve as long as they respect this grammar.

13. Status, determinism, and evolution

The ConstructOS grammar is designed to be conservative and long-lived. Node names, regions, and scope axes are expected to remain stable over time so that tools, runtimes, and design systems can safely depend on them.

ConstructOS favors deterministic systems over ad-hoc mutation. The same structure, data, and scope should always produce equivalent outputs. Violations of the grammar (illegal child nodes, cross-context mixing, nested feeds, or misuse of scope attributes) are intended to fail deterministically so that tools can detect and correct them instead of silently drifting.

New capabilities are added as interpretation layers (themes, schemes, runtimes, utilities) rather than by changing the core grammar. When extensions are needed, they should follow the same patterns shown in this document: one wrapper per node, clear attributes, and no mixing of structural concerns with visual identity.

This file is the canonical reference for the ConstructOS structural standard model. Implementations, examples, and language bindings may evolve independently, provided they preserve this underlying grammar.

ConstructOS is framework-agnostic and style-free by design. Use this document as the structural reference; treat themes, schemes, runtimes, assets, and utilities as replaceable layers on top of this grammar.

This file is intentionally verbose. It is meant to be read, parsed, and regenerated by tools that understand ConstructOS. The structural grammar should remain stable even as implementations, frameworks, and design systems change over time.
